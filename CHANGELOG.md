- **Transcript backend actually delivers captions live (2026-10-31, same day)**: the first live tests returned NO_CAPTIONS for videos that plainly have subtitles. ### Fixed
- **Dead-click traps on the guide page + homepage dropzone made clickable (2026-10-29)** (`src/pages/textToSpeechPillar.js`, `public/app.js`), from the same 2026-10-29 Clarity sweep: the /text-to-speech guide's four feature cards (Human-Grade AI, Document Upload, Instant MP3, 100% Free) looked like buttons but were static divs — one mobile user tapped them ~10 times in 6 seconds and never reached the tool (rage clicks) — and on the homepage only the small "Browse File" label inside the upload dropzone was clickable, so taps on the dropzone's icon/text were dead clicks. The four cards are now real links to the tool homepage (same card styling, block anchors), and the whole dropzone opens the file picker on click (the Browse File label keeps its native behavior; the handler skips label clicks to avoid a double open) with a pointer cursor.
- **Voice generation stalls fixed (2026-10-29)** (`src/providers/edge/edgeProvider.js`, `src/services/queueService.js`, `public/app.js`), found via a filtered Microsoft Clarity sweep (12 recordings sampled from the last 30 days): 150 of 1,421 sessions hit the site's Retry button — Generate left users stuck on "Synthesizing..." with no audio. Three root causes fixed together: (1) **Silent-socket hang** — in the Cloudflare Sockets transport, the 15s `readTimeout` only closed the writer, so when Microsoft's backend accepted the connection and then went silent, `reader.read()` could hang indefinitely and the whole request stalled. Replaced with a stall watchdog: the attempt aborts if no data arrives for 12s (healthy synthesis streams frames continuously, so live streams are never cut) with a 45s absolute cap, partial audio from an aborted stream is discarded, and the caller fails over to the second host instead of hanging. (2) **Sequential chunk synthesis** — a 6-chunk script took ~14s inside one request (measured live, 2026-10-29) and long scripts could pass 45s+; chunk synthesis now runs with bounded concurrency (3 workers, results kept in chunk order). (3) **Frontend/status fragility** — `pollJobProgress` gave up after 15 polls (~15s) even while a job was progressing and never verified the final audio download (a 404 error body could be "played" as audio, silently); it now polls up to ~3 minutes, gives up only after 60s without progress, tolerates brief poll errors, and verifies + retries the audio download (ok + size check). The instant-audio path also requires a sane blob size before playing. (4) **Storage integrity** — `queueService.saveJob` set `hasAudio: true` in the KV meta even when the R2 put had failed, so status claimed COMPLETED and the download 404'd; the R2 put is now retried once, `hasAudio` reflects reality, and a completed job whose audio could not be stored is recorded as FAILED with a clear retry reason. Local note: this sandbox cannot reach Microsoft's speech backend (original code fails identically, verified via git stash), so verification is the live before/after API timing.
- **Read-Along highlight sync fixed (2026-10-29)** (`public/app.js`): the user spotted via Microsoft Clarity session recordings that the word-by-word highlight did not move with playback. Server side was verified healthy first (live `/api/generate` returned `readAlongAvailable: true` with correct per-word timings). Three frontend weaknesses were fixed together: (1) `findActiveWordIdx` returned -1 in the pauses between words, so the highlight vanished at every sentence gap and after the final word — it now holds the current word until the next word starts (karaoke-style); (2) painting depended solely on a `requestAnimationFrame` loop, which stalls in throttled/backgrounded rendering contexts — painting is now also driven by the audio element's `timeupdate` event (~4x/sec while playing) via a shared `paintReadAlongFromAudio()`; (3) the animation-frame loop could die silently on a single bad frame or a dead loop on replay — the tick is now exception-guarded and a `play` listener revives the loop and repaints on any (re)play while Read-Along is on. The `seeked` handler also repaints immediately. No behavior change for normal playback/download; the box still only opens when the user toggles Read-Along on.
- **Voice generation restored — Edge TTS Sec-MS-GEC v2 protocol (2026-10-27)** (`src/providers/edge/edgeProvider.js`): Microsoft migrated the Read Aloud backend — nodes now reject the legacy v1 `Sec-MS-GEC` token (SHA-256 only, `Sec-MS-GEC-Version: 1-*`) with a 403 WebSocket handshake, so every `/api/generate` call failed ("All providers failed" → frontend "Unexpected server response"). The provider now generates the Edge 155 v2 token — `<16-hex CS64 patent hash>-<64-hex SHA-256>` over `Copyright (C) Microsoft Corporation. All rights reserved.` + 5-minute-bucketed FILETIME ticks + the trusted client token, implemented in JS with exact 32-bit wrapping arithmetic and verified byte-for-byte against a captured Edge 155 browser token — and sends it with `Sec-MS-GEC-Version: 2-155.0.4283.45` and an Edge 155 user-agent/origin. The raw-WebSocket retry now diversifies by transport instead of repeating the identical request: attempt 2 uses the classic `speech.platform.bing.com` host with the v2 token (what Edge 155 itself does), attempt 3 uses the new `api.msedgeservices.com/tts/cognitiveservices/websocket/v1` endpoint with the trusted token as `Ocp-Apim-Subscription-Key`. Root cause was external (Microsoft protocol migration, tracked publicly as edge-tts issue #490), not the 2026-10-26 Phase 1 function-layer changes — API plumbing was verified healthy (400 JSON path) before the fix.
- **Security headers + CSP + HTML edge caching from the function layer (2026-10-26)** (`functions/[[path]].js`), from the 2026-10-26 SEO audit (Phase 1, user approved; observability follow-up same day: stored cache copy drops `max-age=0` — s-maxage-only — and responses carry an `X-Edge-Cache: HIT/MISS/PASS` header; live-verified HITs on repeat same-datacenter requests with TTFB down vs MISS at the same datacenter): `public/_headers` applies only to static assets, so its `/*` security block reached 1/109 pages and no CSP existed anywhere. The same layer now edge-caches anonymous GET HTML (no query string, no cookies/auth, non-API) in the Cloudflare Cache API for 1h with stale-while-revalidate, replacing the previous `cf-cache-status: DYNAMIC` on 109/109 pages (crawl-measured TTFB median 0.499s). Cache failures are swallowed so a cache error can never break a page.
